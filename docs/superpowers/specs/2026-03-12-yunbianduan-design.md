# 云边端就医自助终端监测及预警系统 — 设计规格文档

**日期：** 2026-03-12
**版本：** v1.0
**技术路线：** KubeEdge + Spring Cloud（方案二）

---

## 1. 项目概述

基于云边端协同架构，面向单医院部署的就医自助终端监测及预警系统。覆盖挂号预约、缴费支付、报告打印查询、叫号导诊、医保结算五类业务场景，具备硬件异常、业务异常、安全异常全类型检测能力。

### 核心指标约束

| 指标 | 目标值 |
|------|--------|
| 云边端全链路传输延迟 | < 50ms（仿真验证） |
| 支付验证算法响应时间 | < 1 秒 |
| 异常检测准确率 | ≥ 98% |
| 异常响应时间 | < 5 秒 |
| 流程效率提升 | ≥ 10% |
| 患者满意度提升 | ≥ 15% |

| 层级 | 职责 | 关键技术 |

| 边缘层 | 本地实时处理、断网续传、首级异常过滤 | KubeEdge EdgeCore、Drools、Mosquitto |
| 云端层 | 全局管控、复杂分析、持久化、可视化 | Spring Cloud、Kafka、K8s |

## 3. 通信协议与 50ms 延迟仿真

### 通信协议栈

| 链路 | 协议 | 加密 | 预期延迟 |
|------|------|------|----------|
| 终端 → 边缘 | MQTT 3.1.1 | TLS 1.3 | < 5ms |
| 边缘 → 云端（实时数据） | gRPC (HTTP/2) | mTLS 双向证书 | < 30ms |
| 边缘 → 云端（事件流） | Kafka over TLS | TLS 1.3 | < 20ms（异步） |
| 云端内部 | REST / gRPC | K8s NetworkPolicy | < 2ms |
| 告警下发（云→边→端） | MQTT | TLS 1.3 | < 10ms |

### 端到端延迟预算

```
终端上报 → 边缘处理 → 云端响应 → 告警回传
   5ms    +   10ms   +   25ms   +   10ms  = 50ms ✅
```

### 延迟仿真方案

使用 Linux `tc netem` 在 KubeEdge EdgeCore 所在 Pod 网络命名空间注入延迟：

```bash
# 模拟边缘→云端 WAN 链路，注入 25ms 延迟 + 2ms 抖动
tc qdisc add dev eth0 root netem delay 25ms 2ms distribution normal

# 模拟终端→边缘局域网，注入 5ms 延迟
tc qdisc add dev eth0 root netem delay 5ms 1ms
```

**仿真验证流程：**
1. 启动仿真终端客户端（Java，模拟 20 台终端并发上报）
2. 注入 tc netem 延迟参数
3. 采集各链路 P50/P95/P99 延迟指标（Prometheus + Grafana）
4. 调整 MQTT QoS 级别（QoS=1）和 gRPC keepalive 参数
5. 压测目标：P95 < 50ms，P99 < 80ms

### 安全传输机制

- **证书体系：** 自签 CA 签发边缘节点证书，KubeEdge 内置证书轮换
- **MQTT 认证：** 用户名/密码 + TLS 客户端证书双重认证
- **数据完整性：** 消息体 HMAC-SHA256 签名，防篡改

## 4. 核心业务微服务与支付验证

### 微服务拆分

```
API Gateway (Spring Cloud Gateway)
路由 / 限流(Resilience4j) / JWT鉴权
  ├── 挂号服务
  ├── 支付服务
  ├── 报告服务
  ├── 叫号服务
  └── 医保结算服务
       └── Kafka 事件总线
           MySQL（业务库）Redis（缓存/会话）
```

### 支付验证 <1s 设计

```
终端发起支付请求
      ↓
边缘层预验证（本地缓存患者信息，~50ms）
      ↓
支付服务接收（Spring Boot，Kafka异步通知）
      ↓
┌─────────────────────────────────┐
│ 并行执行（CompletableFuture）    │
│ ① 医保资格验证  ~200ms          │
│ ② 支付渠道预授权 ~300ms         │
│ ③ 风控规则检查  ~100ms（Redis） │
└─────────────────────────────────┘
      ↓ 合并结果 ~50ms
支付结果返回终端（总计 ~600ms）✅
```

**关键优化点：**

| 优化手段 | 效果 |
|----------|------|
| 边缘本地缓存患者基础信息（Redis） | 减少云端查询 ~200ms |
| 三路并行验证（非串行） | 节省 ~300ms |
| 医保接口连接池预热 | 减少首次建连开销 |
| 支付结果 Redis 幂等缓存（60s） | 防重复支付，毫秒级响应重试 |

## 5. 异常检测系统

### 双引擎架构

```
终端上报数据流（MQTT）
        ↓
边缘层：Drools 规则引擎（实时，<500ms）
├── 硬件异常规则：终端离线/打印机故障/读卡器异常
├── 业务异常规则：支付超时>30s / 队列积压>50人
└── 触发本地告警 → MQTT 推送终端 + 上报云端
        ↓（原始数据流 → Kafka）
云端层：统计分析引擎（批+流，<5s）
├── Flink 流处理：滑动窗口统计（1min/5min）
├── 安全异常：异常刷卡频率/支付金额突变检测
└── 复杂告警聚合 → 预警中台 → 通知运维人员
```

### 98% 准确率实现策略

| 机制 | 说明 |
|------|------|
| 规则分级 | P0（立即告警）/ P1（确认后告警）/ P2（记录观察） |
| 时间窗口确认 | 异常持续 >3次心跳（15s）才升级为告警，过滤瞬时抖动 |
| 历史基线对比 | 云端维护每台终端历史正常指标基线，偏差 >3σ 才触发 |
| 告警去重 | Redis 去重窗口，同类异常 5 分钟内只告警一次 |

**检测指标覆盖：**

- **硬件层：** 心跳超时 / 外设状态码 / 温度电量（如有传感器）
- **业务层：** 事务成功率 / 平均处理时长 / 队列深度
- **安全层：** 单卡高频刷卡 / 非工作时段操作 / 支付金额异常

### 响应时间保障（<5s）

```
异常发生
  ↓ 0-500ms   边缘 Drools 规则命中 → 本地告警
  ↓ 500ms-2s  Kafka 推送云端
  ↓ 2s-4s     Flink 窗口计算确认
  ↓ <5s       告警推送运维大屏 + 短信/钉钉通知 ✅
```

## 6. 流程优化与患者满意度提升

### 流程优化（≥10%）

| 优化点 | 当前痛点 | 解决方案 | 预期提升 |
|--------|----------|----------|----------|
| 智能分诊导流 | 患者不知道去哪个终端 | 边缘层实时队列感知，终端屏显示最短等待路径 | 等待时长 -15% |
| 支付流程简化 | 医保+自费需多次操作 | 统一支付入口，自动识别医保资格，一键结算 | 操作步骤 -30% |
| 故障预测性维护 | 终端故障影响业务 | 异常检测提前发现设备劣化趋势，主动派工维修 | 故障中断 -20% |
| 报告自动推送 | 患者需反复查询 | 检验完成事件触发，主动推送至终端/手机 | 等待查询次数 -50% |

**量化基准：** 通过仿真终端压测采集 T0 数据，目标 T0 × 90%。

### 患者满意度提升（≥15%）

四个干预维度：

1. **等待体验：** 实时叫号进度展示 + 预计等待时间（边缘队列数据）
2. **操作体验：** 大字体/语音引导/流程步骤 ≤4 步
3. **异常恢复：** 终端故障 30 秒内自动引导至备用终端
4. **反馈闭环：** 每次业务结束后 1 题满意度采集（存入云端分析）

**满意度度量：** 终端内置 1-5 星单题采集，云端按终端/时段/业务类型分维度统计，目标评分 T0 × 115%。
